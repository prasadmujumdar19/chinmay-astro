# VPS Monitoring (PDF-23 / PDF-24 / PDF-26)

n8n-independent safety nets that run on the Linode VPS via cron and alert the
admin in Slack **without** going through n8n (n8n may itself be the thing that
is down). "Chinmay finds out before the customer does."

## Layout (on VPS)

```
/mnt/chinmay-astro-data/monitoring/
  alert.sh           # shared DD-G alert helper (source-able): send_alert / clear_alert
  health-check.sh    # PDF-23 — containers / Postgres / disk / cloudflared
  cred-check.sh      # PDF-24 — Gemini + WhatsApp credential probes
  extract-secrets.sh # (re)generate secrets.env from n8n's credential store
  secrets.env        # chmod 600, VPS-ONLY, NEVER committed (Slack token + channel + Gemini/WA creds)
  state/             # repeat-suppress state (one file per alert key)
```

Committed (secret-free) copies live in repo `scripts/monitoring/`.

## Alert path (DD-G, refined 2026-06-20)

Alerts POST to Slack `chat.postMessage` (channel `chinmay-admin-commands`,
`C0A5B0ZE81E`) using the **existing n8n Slack bot token**, extracted once into
`secrets.env` so the alert path does not depend on n8n being up. The
"swappable destination" is the channel id + token in `secrets.env`.

**Repeat-suppress:** each alert key fires at most once per 6h (`SUPPRESS_SECONDS`,
default 21600) while the fault persists; recovery posts a one-shot `:white_check_mark:`
and clears the key's state file.

## Secrets

`secrets.env` is generated by `extract-secrets.sh` (run on the VPS as root),
which pulls the live values from n8n's encrypted credential store
(`n8n export:credentials --decrypted`) and writes them straight to a chmod-600
file. Nothing is printed; nothing is committed. **Re-run it after rotating any
of these credentials in n8n.**

## Cron (root) — host is UTC; IST = UTC+5:30

```
0 * * * *    /mnt/chinmay-astro-data/monitoring/health-check.sh        # PDF-23 hourly
30 6,18 * * * /mnt/chinmay-astro-data/monitoring/cred-check.sh gemini   # PDF-24 Gemini 06:30+18:30 UTC = 12:00+00:00 IST
0 7 * * *    /mnt/chinmay-astro-data/monitoring/cred-check.sh whatsapp # PDF-24 WhatsApp daily (07:00 UTC ≈ 12:30 IST)
```

**IPv4 note:** the Gemini API key is IP-restricted to the VPS IPv4. `cred-check.sh`
forces `curl -4` so probes egress over the allowlisted IPv4 path (an IPv6 call
returns HTTP 403 "IP restriction" — a false negative).

## Deploy / update

Edit the committed copy in `scripts/monitoring/`, then `scp` to the VPS dir and
re-run `extract-secrets.sh` if credentials changed. The cron entries above are
installed in root's crontab.
