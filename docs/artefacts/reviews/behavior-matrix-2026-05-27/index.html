Cross-cutting concerns

X1 — Rapid consecutive messages

WhatsApp delivers each message as a separate webhook POST. n8n triggers a new execution per webhook with no built-in queue or per-user lock.

Live: Three concurrent executions read users.status independently and route per that snapshot. If one of the three is STOP, REBOOK, or Payment Completed, a race condition can produce extra Slack posts after opt-out or extra Gemini replies after closure. Usually fine, occasionally visible to admin.

Recommendation (post-MVP): Add a user-facing notice during onboarding: "Replies usually take a few seconds — please send one message and wait for our response."

X2 — Multi-line single message

WhatsApp delivers a single message as messages[0].text.body including any \n. ONE webhook, ONE execution — no race.

Live: WF-20 keyword check uses exact-match on uppercased trimmed text. A message like "STOP\nthanks" trims to "STOP\nTHANKS" — not exact 'STOP' — so does NOT opt the user out. Intentionally strict (avoids false positives).

Verdict: Working.

X3 — Admin action race

Admin types APPROVE PAYMENT or CLOSE while user sends a message. Two concurrent executions read users.status at different moments; the message may route as the old or new state. Worst case: one extra Slack post or canned reply.

Verdict: Acceptable race window — no code fix for MVP.

X4 — Post-MVP user notice — response latency

Add one paragraph to WF-22's payment instructions:

📝 A quick note: our replies usually arrive within a few seconds. If you have multiple things to ask, please send one message and wait for our response — sending several messages in quick succession can confuse our system.
