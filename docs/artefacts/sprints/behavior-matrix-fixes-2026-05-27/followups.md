### [2026-05-29] Consumer-contract acceptance must be an explicit verification gate for contract-PRODUCER workflows
- **Target:** `build-workflow` Step 6 (add a verification sub-step) + `impact-analysis` Step 3 (promote the "children" line from a generic checklist item to a mandatory consumer-acceptance check for contract producers).
- **Observed on:** BMX-P2-WF01 (WF-01 rebuild). WF-01 is a **data-envelope producer** — its whole job is to emit the canonical §2.1 envelope to WF-02/WF-21/WF-26. During verification I *spontaneously* ran a parent-contract check ("does WF-00 consume WF-01's return?") but did **not** proactively run the symmetric, higher-value **consumer**-contract check ("does each downstream consumer's entry guard accept, field-for-field, the exact payload WF-01 emits?"). User flagged it; the consumer checks (WF-26 live guard match, WF-21 no-guard reads, WF-02 co-design) were then run and all passed — but only reactively.
- **Gap:** for a contract *producer* (envelope creator, router, any workflow whose output shape is consumed by a downstream entry guard), the consumer-acceptance direction is MORE important than the parent direction, yet the skills make the parent check the natural habit (Step 6b runtime-probe + the worked "parent return" example) and leave consumer acceptance as a soft `impact-analysis` checklist line with no field-for-field verification step. The asymmetry trained the wrong proactive default.
- **Fix:** add a `build-workflow` Step 6 sub-step — *"Consumer-contract acceptance (required when the change alters an output payload/contract consumed downstream): for each downstream consumer, read its entry guard / first-consuming node and confirm the emitted payload satisfies it field-for-field (names, types, required-vs-null, discriminator values). Symmetric to — and higher priority than — the parent-return check."* Mirror in `impact-analysis` Step 3 by upgrading the children line to require the field-for-field acceptance check for contract producers, with a worked Good example (the WF-01→WF-26 guard match table).
- **Priority hint:** medium (correctness-of-verification; the missing proactive check is exactly the class that produces silent mis-route / entry-guard-throw regressions the data-contract discipline exists to prevent). Flush via `flush-plugin-improvements` at batch boundary.
- Backing memory: [[feedback_data_contract_discipline]].

### [2026-05-29] build-workflow Step 6a dangling-ref scan must also cover connection TARGET names, not just `$('…')` expression refs
- **Target:** `build-workflow` Step 6a (and `impact-analysis` Step 2a — same scan).
- **Observed on:** BMX-P2-WF02. Renamed node `Is Text Message?` → `Existing-User Text?`; the transform updated the node's own outgoing-connection KEY and all `$('…')` expression refs, but missed the **incoming connection target** (`Detect Route.main → "Is Text Message?"`), leaving a dangling connection target. Step 6a's scan (which only greps `$('<name>')` expression refs) returned clean — the defect was caught one step later by `n8n_validate_workflow` ("Connection to non-existent node"), which also produced a cascade of false "not reachable from trigger" warnings on every downstream node.
- **Gap:** Step 6a as written scans only `$('NodeName')` expression references. n8n connections reference nodes by NAME in two places — the connection KEY (source) and each entry's `.node` (target). A rename that updates the key + expressions but misses a target leaves a silent broken edge that Step 6a does not flag. It happened to be caught by Step 6b here, but 6b is not always run (skipped when only Set/IF/Switch touched), so the gap is real.
- **Fix:** extend the Step 6a scan to also walk `.connections[*].main[*][*].node` for any reference to a removed/renamed name (in addition to the `$('…')` grep). One jq pass: `jq '[.connections[].main[][].node] | map(select(. as $n | $REMOVED | index($n)))'`. Flag any hit as a BLOCKER identical to a dangling expression ref.
- **Priority hint:** medium (cheap deterministic check; prevents a silent broken-edge class on every rename/remove). Flush via `flush-plugin-improvements` at batch boundary.
