## 🔴 P0 — Security / Data Integrity

### TD-NEW-001 · GitHub PAT stored in `~/.claude/settings.json` — synced via Google Drive

**Finding:** `~/.claude/settings.json` (or `settings.local.json`) contains a real GitHub Personal Access Token. Because the file lives under `~/.claude/` which is Google Drive–synced, the token is exposed in cloud storage.

**Risk:** Anyone with access to the Google Drive can read the PAT and push to any repo it has access to.

**Fix:** Rotate the PAT immediately. Switch to `gh auth login` (keychain-backed) so the token is stored in the OS keychain, not in a synced file.

**Note:** This is outside the project codebase — action required on the user's machine, not in this repo.

---

### TD-NEW-002 · WF-01 opted-out routing is dead code — opted-out users can never re-engage

**Finding:** `WF-01` `Lookup: Blacklisted Users` SELECTs both `blocked` and `opted_out`. The downstream `Layer 3` node unconditionally sets `securityCheck='REJECTED'` for any hit. The `Opted Out?` IF is unreachable and the `Route Opted-Out to WF-21` node is dead code.

**Impact:** Users who previously sent STOP (`status=opted_out`) are permanently locked out — they cannot re-engage by messaging again as specified in J-21 and the state machine.

**Fix:** Split `Layer 3` routing: emit `OPTED_OUT` when `status='opted_out'` (route to WF-21 welcome), emit `REJECTED` only when `status='blocked'`.

---

### TD-NEW-003 · WF-25 (Intent Classifier) cannot emit `stop_intent` — all stop_intent branches are dead code

**Finding:** WF-25 Gemini prompt enumerates 7 intents with no `stop_intent`. The `Parse Intent VALID` whitelist also excludes it. Every `stop_intent → WF-47` branch added by TD-028 (WF-30, WF-31) and TD-032 (WF-44) is unreachable because WF-25 will never return that value.

**Fix:** Add `stop_intent` to the Gemini prompt's intent list and to the `VALID` whitelist in `Parse Intent`.

---

### TD-NEW-004 · WF-20 (Keyword Handler) is never called — STOP/HELP/REBOOK keywords broken in production

**Finding:** Static analysis across all 28 workflows shows zero `executeWorkflow` callers for WF-20 (`LgIDj1v4ZbCPlX25`). WF-02 routes text messages straight to status-specific workflows without passing through WF-20. Combined with TD-NEW-003, no STOP keyword path functions end-to-end.

**Fix:** Wire WF-20 into WF-01 or WF-02 as the first text-handling step, before routing to status-specific workflows.

### TD-NEW-007 · WF-40 (Active Consultation Relay) has no STOP intercept

**Finding:** During `consultation_active`, if a user sends "STOP", the message is relayed verbatim to Chinmay in Slack instead of being intercepted. Per J-19, the bot should respond with a specific message explaining the consultation cannot be ended by the user and no state change should occur.

**Fix:** Add a STOP keyword check at the start of WF-40 before the relay step. If message is "STOP", send J-19 response and exit without relaying.

### TD-NEW-008 · WF-43 (Post-Consultation Handler) has no `stop_intent` branch

**Finding:** After TD-NEW-003 is fixed and WF-25 can emit `stop_intent`, WF-43's intent router has no branch for it. A `consultation_closed` user expressing desire to stop would fall through to the default branch.

**Dependency:** Requires TD-NEW-003 to be fixed first.

**Fix:** Add `stop_intent` branch in WF-43 that calls WF-47 (or sends guidance to use STOP keyword per design).

### TD-NEW-009 · WF-22 "User Already Exists" branch sends empty `workflowInputs` to WF-50

**Finding:** The `Call 'WF-50 Send WhatsApp'1` node on the "User Already Exists" path passes empty `workflowInputs` — the user receives no message when re-submitting the form.

**Fix:** Populate the WF-50 call with `phoneNumber` and a re-engagement message body (e.g., "We already have your details on file. [status-specific next-step guidance]").

### TD-NEW-010 · WF-11 STATS command is unroutable — `outputKey` mismatch

**Finding:** `Parse Command` emits `commandType=STATS` but the downstream `Switch` node uses `outputKey='STATUS'`. The STATS branch is unreachable — admin STATS command produces no response.

**Fix:** Correct the Switch `outputKey` to `'STATS'`.

---

### TD-NEW-011 · WF-25 passes `userStage` which is always null — classifier noise

**Finding:** All callers pass `userStage` to WF-25, but the `users` table has no `stage` column. WF-25 always receives `null` for this field. The Gemini prompt references it, introducing unnecessary noise in classification.

**Fix:** Remove `userStage` from all WF-25 call inputs and from the Gemini prompt. Alternatively, add a `stage` column to the `users` table if it was always intended to exist.

## 🟡 P2 — Code Hygiene

### TD-NEW-012 · WF-50 has Meta `phone-number-id` hard-coded in the URL

**Finding:** WF-50 HTTP Request URL contains the phone number ID (`1104226366097236`) as a literal string. If the WABA or phone number changes, every WF-50 URL must be updated manually.

**Fix:** Store as an n8n environment variable (`WA_PHONE_NUMBER_ID`) and reference via `{{ $env.WA_PHONE_NUMBER_ID }}`.

---

### TD-NEW-013 · WF-60 writes orphan rows with fake `userId=9`, `consultationId=2` as fallbacks

**Finding:** WF-60 code nodes have hardcoded fallback values (`userId=9`, `consultationId=2`) used when upstream data is missing. Orphan log rows are silently written with fabricated foreign keys.

**Fix:** Remove the fallback values. If `userId` or `consultationId` are missing, skip the write (or log to n8n execution error output) rather than fabricating data.

---

### TD-NEW-014 · WF-22 has 7 disabled stale nodes including a schema-prefix regression hazard

**Finding:** WF-22 contains 7 disabled nodes. One of them (`Update User in DB`, disabled) contains `UPDATE users` with no `chinmay_astro.` prefix — a TD-001 regression waiting to happen if anyone re-enables it. The others are dead code from earlier iterations.

**Fix:** Delete all 7 disabled nodes from WF-22. The active path is the only one that should remain.

### TD-NEW-015 · WF-00 has 6 disabled webhook-path nodes on the active webhook path

**Fix:** Delete the 6 disabled nodes from WF-00.

### TD-NEW-016 · No retry/timeout on external HTTP nodes in WF-50, WF-22 encryption call, WF-43

**Finding:** WF-25 already has `retryOnFail=true, maxTries=3, timeout=10000` on its Gemini HTTP Request. WF-50 (Meta API call), WF-22 (encryption-svc call), and WF-43 (Gemini call) have no retry or timeout configured.

**Fix:** Add `retryOnFail=true, maxTries=3, timeout=10000` to all external HTTP Request nodes across WF-50, WF-22, and WF-43.

### TD-NEW-017 · WF-22 `Ensure Slack Channel Exists` node still has old name from pre-TD-007

**Finding:** The TD-007 rename of the WF-52 call node in WF-22 (`Call WF-52 (Create User Channel)` → `Ensure Slack Channel Exists (WF-52)`) did not land in the exported JSON. The stale name that confuses AI-generated fixes is still present in the export.

**Fix:** Re-export WF-22 after confirming the rename is saved in n8n.

---

### TD-NEW-018 · `messages.created_at` is `timestamp without time zone` — should be `timestamptz`

**Finding:** All other timestamp columns in the `chinmay_astro` schema use `timestamptz`. `messages.created_at` uses `timestamp` (without time zone), creating inconsistency and potential off-by-offset bugs when comparing across tables.

**Fix:**
```sql
ALTER TABLE chinmay_astro.messages
  ALTER COLUMN created_at TYPE timestamptz
  USING created_at AT TIME ZONE 'UTC';
```

---

### TD-NEW-019 · n8n execution history grows indefinitely — no pruning configured

**Finding:** n8n defaults to retaining all execution records forever. At even modest usage (100 users × 10 interactions each), this will bloat `execution_entity` and `execution_data` tables significantly over months.

**Fix:** Set environment variables in Docker Compose:
```
EXECUTIONS_DATA_PRUNE=true
EXECUTIONS_DATA_MAX_AGE=336
```
(336 hours = 14 days)

---

### TD-NEW-020 · No HMAC verification on Meta webhook (WF-00) or Slack events (WF-10)

**Finding:** Both WF-00 and WF-10 are publicly reachable via CF Tunnel Bypass and accept any payload without verifying the sender. Meta requires `X-Hub-Signature-256` verification; Slack requires `X-Slack-Signature` HMAC verification.

**Risk:** Forged webhooks can trigger any workflow path — including payment approval, user blocking, message relay.

**Fix:**
- WF-00: Verify `X-Hub-Signature-256` HMAC-SHA256 against Meta app secret before processing.
- WF-10: Verify `X-Slack-Signature` HMAC-SHA256 against Slack signing secret before processing.

*Note: Partially overlaps with STATUS.md TD-03 and TD-04 (carried forward below).*
